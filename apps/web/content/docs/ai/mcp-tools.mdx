The MCP server exposes structured tools for discovery, project creation, and existing-project
updates. Call the live guidance and schema tools instead of guessing fields from prose: the schema
is the authoritative contract.

## Recommended workflows

### Discover a stack

1. Call `bfs_get_guidance`.
2. Use `bfs_list_presets` when a known starting point is useful.
3. Use `bfs_recommend_stack` for a product brief, or `bfs_get_schema` for direct selection.
4. Pass the proposed stack through `bfs_check_compatibility`.

### Create a project

1. Complete the discovery workflow.
2. Call `bfs_plan_project` to generate the file tree in memory.
3. Show the plan and adjustments to the user.
4. After approval, call `bfs_create_project` with the same stack fields.
5. Report the returned install command; MCP does not install dependencies.

### Update an existing stack

1. Call `bfs_get_guidance`.
2. Call `bfs_plan_stack_update` with an absolute `projectDir` and the scaffold-time fields to
   change.
3. Review compatibility adjustments, conflicts, manual-review blockers, architecture changes, and
   migration steps.
4. After approval, call `bfs_apply_stack_update` with the same fields. Set
   `acknowledgeArchitectureChange: true` only when the user accepted an architecture change.
5. Report the returned install command and any manual migration work.

Use `bfs_plan_addition` and `bfs_add_feature` only for the narrower addon, web-deploy, and
server-deploy workflow.

<Callout kind="warn" title="Write and migration behavior">
Planning tools are read-only. Create, apply, and add tools write files but do not install
dependencies. Stack updates refuse to overwrite user-edited generated files. Architecture updates
do not migrate application data or schemas automatically.
</Callout>

## Discovery and validation tools

### `bfs_get_guidance`

Returns current workflow rules, field semantics, ambiguity rules, and constraints. It has no input
and never writes files. Call it first because its output evolves with the server.

### `bfs_get_schema`

Returns valid options for one `category` or all categories. Pass `ecosystem` to limit the response
to the relevant field family. It is read-only.

```json
{ "category": "database", "ecosystem": "typescript" }
```

### `bfs_list_presets`

Lists each ready-made preset with its ID, name, description, ecosystem, and stack summary. It has
no input and is read-only. Treat the response as authoritative instead of keeping a local preset
list.

### `bfs_recommend_stack`

Accepts a required natural-language `brief` plus optional `ecosystem` and `projectName`. It uses
deterministic rules—not another model—to return a compatibility-validated config, rationale,
adjustments, nearest preset, graph metadata, and reproducible CLI command. It is read-only.

```json
{
  "brief": "A B2B SaaS with organizations, billing, and PostgreSQL",
  "projectName": "control-plane"
}
```

### `bfs_check_compatibility`

Accepts an `ecosystem` and supported stack fields. It returns adjusted selections, changes,
compatibility issues, and whether issues remain. It is read-only. Use `bfs_get_schema` to discover
the exact current fields and value shapes before calling it.

## New-project tools

### `bfs_plan_project`

Generates the proposed project in memory. It accepts scaffold-time fields and returns the generated
file/directory summary plus graph-backed stack metadata. It never writes files.

```json
{
  "projectName": "my-app",
  "ecosystem": "typescript",
  "frontend": ["tanstack-router"],
  "backend": "hono",
  "runtime": "bun",
  "database": "sqlite",
  "orm": "drizzle"
}
```

### `bfs_create_project`

Requires `projectName`; optional `targetDir` is the absolute parent directory. It accepts the same
scaffold-time fields as planning, creates the project directory, writes generated files and
`bts.jsonc`, and returns the path, file count, graph metadata, warnings, and install guidance. It
does not install dependencies.

## Existing-project stack tools

### `bfs_plan_stack_update`

Requires an absolute `projectDir` and accepts the same scaffold-time stack fields as project
planning. It compares the requested stack with `bts.jsonc`, computes safe file operations, and
returns compatibility adjustments, conflicts, blockers, architecture changes, migration steps,
and install guidance. It does not write files.

```json
{
  "projectDir": "/absolute/path/to/my-app",
  "email": "resend",
  "addons": ["biome", "github-actions"]
}
```

### `bfs_apply_stack_update`

Requires the same `projectDir` and requested stack fields used for the reviewed plan. It regenerates
only safe scaffold-owned files, preserves user-edited generated files, updates configuration and
the scaffold manifest, and returns the applied result plus install guidance. It does not install
dependencies.

When the plan reports an architecture change, repeat the request with
`acknowledgeArchitectureChange: true` only after the user approves the listed data/schema risks.

## Focused addon and deploy tools

### `bfs_plan_addition`

Requires an absolute `projectDir`. Optional inputs are `addons`, `webDeploy`, and `serverDeploy`.
It reads `bts.jsonc`, identifies new and already-present additions, checks compatibility, and does
not write files.

### `bfs_add_feature`

Requires an absolute `projectDir`. Optional inputs are `addons`, `webDeploy`, `serverDeploy`, and
`packageManager`. It applies the focused addition and updates project metadata without installing
dependencies. Use it only after `bfs_plan_addition` succeeds and the user approves.

## Rules for agents

- Start with `bfs_get_guidance`; use `bfs_get_schema` for exact current field names, value sets, and
  array shapes.
- Keep the ecosystem and field family aligned. Do not convert arrays to scalar strings.
- Apply the exact stack that was planned; if the request changes, plan again.
- Do not call a write tool until the user has reviewed its corresponding plan.
- Surface compatibility adjustments and manual-review blockers instead of silently accepting them.
- After every write, report the returned dependency-install command and relevant test/run commands.

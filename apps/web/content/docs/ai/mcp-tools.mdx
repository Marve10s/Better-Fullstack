The MCP server exposes structured tools for discovery, project creation, and existing-project
updates. Call the live guidance and schema tools instead of guessing fields from prose: the schema
is the authoritative contract.

## Recommended workflows

### Discover a stack

1. Call `bfs_get_guidance`.
2. Use `bfs_list_presets` when a known starting point is useful.
3. Use `bfs_recommend_stack` for a product brief, or `bfs_get_schema` for direct selection.
4. Pass the proposed stack through `bfs_check_compatibility`.

### Create a project

1. Complete the discovery workflow.
2. Call `bfs_plan_project` to generate the file tree in memory.
3. Show the plan and adjustments to the user.
4. After approval, call `bfs_create_project` with the same stack fields.
5. Report the returned install command; MCP does not install dependencies.

### Update an existing stack

1. Call `bfs_get_guidance`.
2. Call `bfs_plan_stack_update` with an absolute `projectDir` and the scaffold-time fields to
   change.
3. Review compatibility adjustments, conflicts, manual-review blockers, architecture changes, and
   migration steps.
4. After approval, call `bfs_apply_stack_update` with the same fields. Set
   `acknowledgeArchitectureChange: true` only when the user accepted an architecture change.
5. Report the returned install command and any manual migration work.

Use `bfs_plan_addition` and `bfs_add_feature` only for the narrower addon, web-deploy, and
server-deploy workflow.

### Inspect, check, and update project files

1. Call `bfs_get_project_status` to recognize the project and inspect lifecycle prerequisites
   without running generated toolchains.
2. Call `bfs_check_project` when the user wants truthful executable verification. Treat missing
   dependencies, targets, or toolchains as failures.
3. Call `bfs_plan_project_update` to compare the project with the currently bundled templates.
4. Review the categorized/hash-bound plan. Structured merge content is exact through 32 KiB per
   file; oversized content is withheld with size/SHA metadata and no token is issued.
5. After approval, call `bfs_apply_project_update` with the same absolute `projectDir` and exact
   token. Set `acknowledgeUnprovenManifestV1: true` only when the plan reports migrated/adopted
   unverified lineage. A missing, stale, modified, cross-project, or bounded-review-ineligible token
   fails closed.
6. Keep the returned recovery transaction ID until `bfs_check_project` passes. If needed, call
   `bfs_recover_project_transaction` with that ID.

Manifest v2 records CLI, generator, template-set, and schema provenance plus lifecycle history.
Transactional apply restores operation-owned writes on failure and returns bounded recovery data.
The current plan still decides eligibility; manifest provenance alone does not define a supported
cross-version upgrade window.

<Callout kind="warn" title="Write and migration behavior">
Planning tools are read-only. Create, apply, and add tools write files. Project checks can fetch
dependencies and write toolchain locks, caches, compiler output, or build artifacts. Stack updates
refuse to overwrite user-edited generated files. Architecture updates do not migrate application
data or schemas automatically.
</Callout>

## Discovery and validation tools

### `bfs_get_guidance`

Returns current workflow rules, field semantics, ambiguity rules, and constraints. It has no input
and never writes files. Call it first because its output evolves with the server.

### `bfs_get_schema`

Returns valid options for one `category` or all categories. Pass `ecosystem` to limit the response
to the relevant field family. It is read-only.

```json
{ "category": "database", "ecosystem": "typescript" }
```

### `bfs_list_presets`

Lists each ready-made preset with its ID, name, description, ecosystem, and stack summary. It has
no input and is read-only. Treat the response as authoritative instead of keeping a local preset
list.

### `bfs_recommend_stack`

Accepts a required natural-language `brief` plus optional `ecosystem` and `projectName`. It uses
deterministic rules—not another model—to return a compatibility-validated config, rationale,
adjustments, nearest preset, graph metadata, and reproducible CLI command. It is read-only.

```json
{
  "brief": "A B2B SaaS with organizations, billing, and PostgreSQL",
  "projectName": "control-plane"
}
```

### `bfs_check_compatibility`

Accepts an `ecosystem` and supported stack fields. It returns adjusted selections, changes,
compatibility issues, and whether issues remain. It is read-only. Use `bfs_get_schema` to discover
the exact current fields and value shapes before calling it.

## New-project tools

### `bfs_plan_project`

Generates the proposed project in memory. It accepts scaffold-time fields and returns the generated
file/directory summary plus graph-backed stack metadata. It never writes files.

```json
{
  "projectName": "my-app",
  "ecosystem": "typescript",
  "frontend": ["tanstack-router"],
  "backend": "hono",
  "runtime": "bun",
  "database": "sqlite",
  "orm": "drizzle"
}
```

### `bfs_create_project`

Requires `projectName`; optional `targetDir` is the absolute parent directory. It accepts the same
scaffold-time fields as planning, creates the project directory, writes generated files and
`bts.jsonc`, and manifest-v2 provenance through the same create core as the CLI. It returns the
path, file count, lifecycle result, graph metadata, warnings, and install guidance. It does not
install dependencies or initialize Git.

## Existing-project stack tools

### `bfs_get_project_status`

Requires an existing project directory containing a valid `bts.jsonc`. It returns the recognized
ecosystem, graph summary, dependency/environment status, verification counts, and lifecycle
prerequisites. It is read-only and does not execute generated toolchains or write project files.
The manifest is optional for inspection: the response reports whether `bts.lock.json` exists and
whether its current contract is supported, its provenance state, and recovery availability. It
never returns a project-update `reviewToken`.

### `bfs_check_project`

Requires a valid `bts.jsonc`, installed project dependencies, and every toolchain required by the
generated targets. It returns every expected target, command/toolchain, execution status, reason,
and an overall `ok` value. Missing dependencies, targets, commands, or toolchains make the result
non-green. It does not directly rewrite generated source, configuration, or the manifest, but its
invoked build tools may fetch dependencies and write locks, caches, compiler output, or build
artifacts; therefore this tool is not annotated read-only. A manifest is not required and no `reviewToken` is produced. Any reported
manifest status does not change the executable check matrix.

### `bfs_plan_project_update`

Requires a valid `bts.jsonc` and compares the on-disk project with the currently bundled templates.
It is read-only and returns categorized drift, conflicts, manual-review items, actionable files,
blockers, and whether apply is allowed. A `reviewToken` is returned only when a supported
versioned `bts.lock.json` baseline is present and every proposed structured merge fits the 32 KiB
per-file review bound. The token binds the canonical project path, raw config and manifest hashes,
categorized actions, intended actionable hashes, preimages, and exact bounded merge bytes. An
oversized merge returns withheld size/SHA/limit metadata and no token. The result includes the
shared lifecycle contract: changes, blockers, provenance, recovery eligibility, and next actions.

### `bfs_apply_project_update`

Requires the same absolute `projectDir`, a supported versioned baseline, prior bounded review, and
its exact 64-character `reviewToken`. Migrated/adopted unverified lineage additionally requires
`acknowledgeUnprovenManifestV1: true`. It writes only actionable template files in a transaction,
advances manifest-v2 history, rolls operation-owned writes back on failure, and returns a recovery
ID and command on success. Missing, stale, changed, cross-project, or oversized-review-ineligible
tokens fail closed. Concurrent edits are preserved and reported instead of being overwritten.

### `bfs_recover_project_transaction`

Requires an absolute `projectDir` and the transaction UUID returned by apply. It restores every
bound preimage for a successful or interrupted transaction exactly once, then returns a shared
`recovered` lifecycle result. Run `bfs_check_project` afterward.

### `bfs_plan_stack_update`

Requires an absolute `projectDir` and accepts the same scaffold-time stack fields as project
planning. It compares the requested stack with `bts.jsonc`, computes safe file operations, and
returns compatibility adjustments, conflicts, blockers, architecture changes, migration steps,
and install guidance. It does not write files.

```json
{
  "projectDir": "/absolute/path/to/my-app",
  "email": "resend",
  "addons": ["biome", "github-actions"]
}
```

### `bfs_apply_stack_update`

Requires the same `projectDir` and requested stack fields used for the reviewed plan. It regenerates
only safe scaffold-owned files, preserves user-edited generated files, updates configuration and
the scaffold manifest, and returns the applied result plus install guidance. It does not install
dependencies.

When the plan reports an architecture change, repeat the request with
`acknowledgeArchitectureChange: true` only after the user approves the listed data/schema risks.

## Focused addon and deploy tools

### `bfs_plan_addition`

Requires an absolute `projectDir`. Optional inputs are `addons`, `webDeploy`, and `serverDeploy`.
It reads `bts.jsonc`, identifies new and already-present additions, checks compatibility, and does
not write files.

### `bfs_add_feature`

Requires an absolute `projectDir`. Optional inputs are `addons`, `webDeploy`, `serverDeploy`, and
`packageManager`. It applies the focused addition and updates project metadata without installing
dependencies. Use it only after `bfs_plan_addition` succeeds and the user approves.

## Rules for agents

- Start with `bfs_get_guidance`; use `bfs_get_schema` for exact current field names, value sets, and
  array shapes.
- Keep the ecosystem and field family aligned. Do not convert arrays to scalar strings.
- Apply the exact stack that was planned; if the request changes, plan again.
- Do not call a write tool until the user has reviewed its corresponding plan.
- Surface compatibility adjustments and manual-review blockers instead of silently accepting them.
- For lifecycle work, inspect before checking, plan before applying, and pass the exact
  `bfs_plan_project_update` token unchanged. Never claim manifest v1 proves generator provenance or
  recovery.
- After every write, report the returned dependency-install command and relevant test/run commands.

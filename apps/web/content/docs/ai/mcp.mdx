### One-line setup commands

Agents reading this page as Markdown get the same commands the tabs above show:

```bash
claude mcp add --transport stdio better-fullstack -- npx -y create-better-fullstack@latest mcp
codex mcp add better-fullstack -- npx -y create-better-fullstack@latest mcp
gemini mcp add better-fullstack npx -y create-better-fullstack@latest mcp
kimi mcp add better-fullstack -- npx -y create-better-fullstack@latest mcp
cmd mcp add better-fullstack -- npx -y create-better-fullstack@latest mcp
code --add-mcp '{"name":"better-fullstack","command":"npx","args":["-y","create-better-fullstack@latest","mcp"]}'
```

### Other MCP clients

Clients that read a config file — Claude Desktop, Zed, Windsurf, Goose — take the same stdio server:

```json
{
  "mcpServers": {
    "better-fullstack": {
      "command": "npx",
      "args": ["-y", "create-better-fullstack@latest", "mcp"]
    }
  }
}
```

VS Code uses `servers` instead of `mcpServers`, Zed uses `context_servers`, and OpenCode/Kilo Code use `mcp` with `"type": "local"`. Swap the launcher for your package manager:

| Package manager | `command` | `args`                                             |
| --------------- | --------- | -------------------------------------------------- |
| npm             | `npx`     | `["-y", "create-better-fullstack@latest", "mcp"]`  |
| pnpm            | `pnpm`    | `["dlx", "create-better-fullstack@latest", "mcp"]` |
| Bun             | `bunx`    | `["create-better-fullstack@latest", "mcp"]`        |
| Yarn            | `yarn`    | `["dlx", "create-better-fullstack@latest", "mcp"]` |

## What the server does

The Better Fullstack MCP server lets agents scaffold and evolve projects through structured tool
calls instead of guessing CLI flags. It handles discovery, recommendations, compatibility checks,
dry-run previews, project creation, broad stack updates, and focused capability/deploy additions.

This page describes the Better Fullstack MCP server. The generated-project `mcp` capability is separate: it writes MCP client/server configuration into a scaffolded app and may run external setup commands.

<Callout kind="info" title="Protocol compatibility is automatic">
The stdio server negotiates both the 2025 MCP protocol family and MCP 2026-07-28 without a
client-specific flag or version pin. Modern clients use the stateless-core request model and
receive cache hints for tool and resource discovery, while older clients continue through the
legacy initialization flow.
</Callout>

## Tools

For full inputs, outputs, examples, and safe write behavior, see the [MCP tools reference](/docs/ai/mcp-tools/).

| Tool                       | Purpose                                                                         |
| -------------------------- | ------------------------------------------------------------------------------- |
| `bfs_get_guidance`         | Returns workflow rules and field semantics. Call this first.                    |
| `bfs_get_schema`           | Returns valid options for configuration categories.                             |
| `bfs_list_presets`         | Lists ready-made stacks and their canonical configuration.                      |
| `bfs_recommend_stack`      | Turns a product brief into a deterministic, validated stack recommendation.     |
| `bfs_check_compatibility`  | Validates a stack and returns adjusted selections with warnings.                |
| `bfs_plan_project`         | Dry-runs project generation in memory.                                          |
| `bfs_create_project`       | Writes a new project to disk.                                                   |
| `bfs_get_project_status`   | Reads project and manifest prerequisites without executing toolchains.          |
| `bfs_check_project`        | Runs every generated target check; build tools may mutate caches/artifacts.     |
| `bfs_plan_project_update`  | Returns a plan-only v1 review token only when bounded content is inspectable.   |
| `bfs_apply_project_update` | Destructively applies token-bound files after explicit v1-risk acknowledgement. |
| `bfs_plan_stack_update`    | Plans any supported scaffold-time stack change in an existing project.          |
| `bfs_apply_stack_update`   | Applies a reviewed stack update without overwriting edited generated files.     |
| `bfs_plan_addition`        | Plans a focused capability or deploy-target addition.                           |
| `bfs_add_feature`          | Applies a focused capability or deploy-target addition.                         |

<Callout kind="info" title="Install behavior">
MCP project creation skips normal dependency installation to avoid long-running agent calls. If the generated project includes the `mcp` capability, that setup may still run external commands for MCP client configuration.
</Callout>

## Recommended tool order

For a new project:

1. `bfs_get_guidance`
2. Discover with `bfs_list_presets`, `bfs_recommend_stack`, or `bfs_get_schema`.
3. `bfs_check_compatibility`
4. `bfs_plan_project`
5. Ask for approval, then `bfs_create_project`.

For an existing project's stack:

1. `bfs_get_guidance`
2. `bfs_get_project_status`, then `bfs_check_project` when executable verification is requested.
3. For current-template drift, call `bfs_plan_project_update`, review it, then pass its exact
   `reviewToken` to `bfs_apply_project_update` after approval. Add
   `acknowledgeUnprovenManifestV1: true` only when the plan reports unverified migrated/adopted
   lineage. Keep the returned transaction ID for `bfs_recover_project_transaction` until checks pass.
4. For capability changes, call `bfs_plan_stack_update` and review conflicts, migration steps, and
   architecture changes.
5. Ask for approval, then `bfs_apply_stack_update` with the same requested fields.

Use `bfs_plan_addition` followed by `bfs_add_feature` only for the narrower capability and deploy-target
workflow.

## Key rules for agents

- Call `bfs_get_guidance` at the start of each workflow and `bfs_get_schema` instead of relying on
  remembered fields or values.
- Set `ecosystem` first, preserve arrays as arrays, and use `none` only where the schema permits it.
- Project planning, creation, and update responses include graph-backed stack metadata.
- A stack update requires an absolute `projectDir`. Plan and apply with the same requested fields.
- Project update apply requires the exact token from a bounded plan. Manifest v2 reports
  generator/template provenance and lifecycle history; apply is transactional and recoverable.
  Migrated/adopted unverified lineage additionally requires explicit acknowledgement.
- Architecture-changing updates do not migrate application data or schemas. Review `migrationSteps`
  and pass `acknowledgeArchitectureChange: true` only after explicit approval.
- Write tools do not install dependencies. Report the returned install command to the user.

[ScaffBench 2](/blog/scaffbench-2) 问了一个问题的最难版本 - 编码代理可以吗
在没有脚手架的情况下，根据提示手写一个真正的全栈项目，然后构建它？答案
是“很少”。

ScaffBench 2.1 将最新模型 **Claude Sonnet 5** 纳入测试 — 与 **Claude 正面交锋
Opus 4.8** 在低推理和最大推理努力上，在扩展套件中的 **13 个硬规格上
八个生态系统**。我们还运行了 **Sonnet 4.6**、**GPT-5.3 Codex Spark**，以及 — 通过 Google 的反重力
CLI — **Gemini 3.5 Flash** 全力以赴，适用于六配置字段。提示路径是最纯粹的
原始能力衡量：代理读取规范并自行写入每个文件。

所有三种配置现已完成完整的 13 规格运行。事情就是这样。

## 排行榜

CORE pass@1 = 项目根据提示进行安装、构建、类型检查和本机编译。更高的是
更好的;成本和步骤按项目计算。

| Claude Opus 4.8 · **低** | **3 / 11** (27%) | $1.63 | 21k | 38 | 96% |
| Claude Opus 4.8 · **最大** | **3 / 11** (27%) | $9.21 | 148k | 99 | 97% |
| Gemini 3.5 闪存 · **高** | **3 / 11** (27%) | — | — | — | 94% |

| GPT-5.3 Codex 火花 · **高** | **1 / 11** (9%) | — | 60k | 12 | 92% |

## Claude Sonnet 5：强烈的本能，更少的构建

Sonnet 5 选择正确的堆栈以及 Opus — **96% 有线，匹配其规格对规格** — 但它
将较少的项目转化为可编译的项目：**2 of 10，而 Opus 的 3 of 11**。而且两人不是
相同规格的陌生人：每种型号都有独特的构造，而另一种则无法构造。

| 规格 | 生态系统 | 作品 4.8·最大 | 十四行诗 5·最多 |
| --- | --- | :---: | :---: |
| `python-ingestion-api` | Python | ✅ 构建 | ✅ 构建 |
| `rust-leptos-axum` | Rust | ✅ 构建 | ❌ 无需构建 |
| `java-spring-jooq-keycloak` | Java | ✅ 构建 | ❌ 无需构建 |
| `elixir-broadway-absinthe` | Elixir | ❌ 无需构建 | ✅ 构建 |
| `ai-search-workbench` | TypeScript | ❌ 无需构建 | ❌ 无需构建 |
| `go-realtime-api` | Go | ❌ 无需构建 | ❌ 无需构建 |
| `multi-dotnet-ops` | 多（TS + .NET） | ❌ 无需构建 | ❌ 无需构建 |
| `ts-svelte-edge-orpc` | TypeScript | ❌超时 | ❌ 无需构建 |
| `dotnet-blazor-cqrs` | .NET | ❌ 无需构建 | ❌ 无需构建 |
| `react-native-expo` | React Native | ❌ 无需构建 | ❌ 无需构建 |
| `frontier-effect-eventsourcing` | TypeScript | ❌ 无需构建 | ⚪ 超时 |
| `frontier-polyglot-proto` | 多 | ⚪ 尚无定论 | ⚪ 超时 |
| `multi-ts-go-grpc` | 多（TS + Go） | ⚪ 尚无定论 | ⚪ 尚无定论 |

Opus 独特地登陆 `rust-leptos-axum` 和 `java-spring-jooq-keycloak`； **十四行诗 5 独特登陆
`elixir-broadway-absinthe`** — 这两款旗舰机型具有真正不同的强项。 `python`
是唯一可靠构建的规范；密集的多服务规格击败了这两者。

Sonnet 5 也是该领域**最繁忙的**运行。每个项目平均 **215 个工具步骤** - 更多
比最大 (99) 的两倍 Opus 和低 (38) 的约 6 倍 Opus — 经过更多的编辑和重试，
并且仍然减少了构建：

Sonnet 5 的阅读：对使用“什么”有很强的意识，但在“组装”密集堆栈方面较弱
一些连贯的东西——而且要达到这个目标需要更努力、更长时间。

## 最大推理并没有购买更多构建

ScaffBench 2 之后的明显假设是模型知道正确的库并且刚刚耗尽
足够的空间来连接它们——因此最大程度的推理应该将未遂事件转变为构建。事实并非如此。

在相同的 13 个规格上，Opus 4.8 的得分**在低值和最高值时相同 — 3/11 无论如何** — **5-10 倍
成本**：

领带隐藏了最有趣的结果。 Max 并没有建造“相同”的三个项目那么低——它
**修复了两个并破坏了两个**：

| 规格 | 作品 4.8·低 | 作品 4.8·最大 |
| --- | :---: | :---: |
| `python-ingestion-api` | ✅ | ✅ |
| `rust-leptos-axum` | ❌ | ✅ **固定** |
| `java-spring-jooq-keycloak` | ❌ | ✅ **固定** |
| `go-realtime-api` | ✅ | ❌ **破了** |
| `multi-dotnet-ops` | ✅ | ❌ **破了** |

额外的深思熟虑**用一个项目的成功换取另一个项目的成功**，而不是提高总数。更多的
思维改变了*哪个*硬堆栈 Opus 正确组装，而不是*多少*。瓶颈不是
推理——这是连贯的组装。

## 更广泛的领域：Gemini 3.5 Flash、Sonnet 4.6 和 Codex Spark

另外三个配置运行起来非常费劲——新来的配置令人惊讶。

- **Gemini 3.5 Flash 在 3/11 与 Opus 4.8 并列榜首**——外部最强表现
  Opus 系列，来自该领域最轻的级别。这也是**唯一建造的模型
  `dotnet-blazor-cqrs`**，并清除了 `java-spring` 和 `python`。通过 **Google 到达
  反重力 CLI** (`agy`) — 独立的 Gemini CLI 现在对于各个层来说已经日落 — 它
  以零暂停的方式完成了所有 13 场比赛。与 Codex 一样，它的未命中偏向于 `install` 失败。
  反重力发出纯文本，因此它的成本/令牌/步骤在这里无法测量。
- **GPT-5.3 Codex Spark 极其简洁：每个项目约 12 个工具步骤**，而 Sonnet 5 为 215 个
  以及作品 38-99。它从未旋转过——它完成了所有 13 项规格，包括两项前沿规格，零分
  超时。但这种速度表现得更松散： Codex 大部分在 **`install`** 处失败（其生成的
  `package.json` / 锁定文件无法解析），而 Claude 模型在 **`build` / `typecheck`** 处失败
  （他们安装得很好，然后不编译）。两种不同的不构建方式。
- **Sonnet 4.6 at high** 是轻量级的 Claude：46 个步骤，1.53 美元/项目，1/11 — 相同
  仅限 python 的结果为 Codex，其成本和步数只是 Sonnet 5 的一小部分。

该模式适用于整个供应商线：每个模型都连接正确的库（92-97％），并且每个
模型很难将它们组装成一个构建——无论是写得简洁（Codex）还是苦涩（Sonnet 5）。

## 免费层：像边境一样有线，或者几乎没有

我们还运行了四个免费模型 - 两个通过 **opencode**（DeepSeek V4 Flash、MiMo V2.5），两个通过
**Kilo 代码**（NVIDIA Nemotron 3 Nano 30B 和 Ultra 550B）。他们分成了两个截然不同的故事。

| 免费模型 | 后端 | 核心pass@1 | 有线库 |
| --- | --- | :---: | :---: |
| DeepSeek V4 闪存 | 开放代码 | **1 / 10** (10%) | 83% |
| 小米V2.5 | 开放代码 | 0 / 9 (0%) | 82% |
| Nemotron 3 Nano 30B | 公斤 | 0 / 1 | 7% |
| Nemotron 3 Ultra 550B | 公斤 | 0 / 3 | 19% |

- **opencode对线与前沿类似，但无法组装。** DeepSeek V4 Flash和MiMo V2.5
  两者都选择了大约 82-83% 的正确库——在付费领域 92-97% 的范围内——但都达到了
  **1/10 和 0/9 版本**。 DeepSeek 的单一构建（再次是 `python`）使其成为最强大的免费模型
  董事会。与其他人一样的故障形状，只是更多：堆栈是正确的，而组件则不然。
- **Kilo Nemotrons 大多根本不产生可测量的项目。** Nemotron 3 Nano 30B 有线
  **7%** 12 个规格中有 11 个规格不确定；超 550B 有线 **19%**。这些读起来不太像构建失败
  比发电失败更严重的是——模型研究、停滞或排放太少而无法验证。超 550B 是
  速度太慢，我们在 13 个中的第 10 个处停止了它，并且标记了其构建挂起验证器的一个规范
  不确定而不是计算。

所以自由楼层并不统一。一个有能力的开放模型可以在*选择*堆栈时匹配前沿——
整个差距在于“构建”它——而较弱的一个永远不会走得足够远，不会导致构建失败。

## ScaffBench 2.1 中的新增功能

- **八个生态系统，13 个规范。** TypeScript、Rust、Python、Go、.NET，现在 **Java**（Spring + jOOQ +
  Keycloak）和 **Elixir** （百老汇 + 苦艾酒），加上 Expo React Native 应用程序和多生态系统
  图——每一个选择都是为了让一个自信的代理人可以选择一个“近”的邻居，并犯下微妙的错误。
- **仅提示的前沿规格。** 有两个规格故意超出了我们自己的生成器的选项空间，
  所以他们只能在快速路径上运行——没有脚手架工可以“欺骗”他们。
- **实际成本会计。** Claude 代码报告 `$0` 订阅，这使得有能力的模型看起来
  自由的。我们现在根据其代币使用情况对每次运行进行定价——这就是上面的最大努力成本的均匀程度
  可见的。
- **经过端到端验证。** 使用评分主机上的 .NET SDK，.NET 和多 .NET 规格为
  现在是真正构建而不是跳过。

## 诚实的部分

Sonnet 的三个规格和 Opus 的两个规格都不是干净的构建结论，基准测试只是有用的
如果我们这么说的话。

<Callout kind="warn">
  **`multi-ts-go-grpc` 对于这两个模型都没有结论 - 这是我们的错误，而不是他们的错误。** 两个代理
  使用子目录（`frontend/package.json`、`backend/go.mod`）中的清单构建了项目，但是
  我们的验证器只查看项目根目录，因此它运行零构建步骤。这些项目可能会很好
  编译；安全带根本无法测量它们，因此它们被排除在上述所有比率之外。
  （下一个修复是教验证器在子目录中查找清单。）
</Callout>

其余的都是超时。 Opus 4.8 在 `ts-svelte-edge-orpc` 推理过程中被中断；十四行诗 5 已售完
两个**前沿**规格上的时钟，但没有产生可衡量的项目。根据我们的 SWE 长凳风格
分类法生成超时是一个模型失败，但它是一个比干净的非构建更软的信号，所以
我们将其单独呈现，而不是将其合并到标题利率中。

## 我们如何得分

<Callout kind="info">
  **CORE 与 Full。** *CORE* 是承载问题 - 项目是否安装、构建、类型检查、
  和本机编译（`cargo check`、`go build`、`dotnet build`、`mvn`、`mix`）？ *完整*增加了品质
  门（lint、格式、测试）。在快速路径上，核心是头条新闻——大多数跑步都没有走那么远。
  每次运行都是 `success`、`model-failure` 或 `infra-inconclusive`；工具链停顿不收费
  模型，以及（根据 SWE-bench）生成超时。
</Callout>

## 要点

- **Sonnet 5 了解堆栈，但组装的构建较少。** 它与库选择领域联系在一起
  （~96% 有线）但在实际编译的项目上存在跟踪（2/10 vs Opus 的 3/11），同时做了最多的事情
  努力实现这一目标（每个项目 215 个步骤）。它确实有自己的优势——它是唯一的配置
  构建了 Elixir 规范。
- **推理努力不是杠杆。** Opus 在最高和最低时构建了相同的 3/11，成本是 5-10 倍 —
  额外的深思熟虑会重新调整堆叠的数量，而不是数量。
- **解决了堆栈选择；相干组装则不然。** ~92–97% 的连线速度为 9–27% 的构建率
  整个故事都在一行中——对于该领域的每一个模型都是如此，并且正是脚手架工缩小的差距，
  这就是为什么 ScaffBench 2 中的 MCP 和 CLI 路径接近 100%，而仅提示则陷入困境。

随着更多模型的登陆，我们将保持排行榜的增长。

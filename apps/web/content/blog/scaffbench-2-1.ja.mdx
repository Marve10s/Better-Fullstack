[ScaffBench 2](/blog/scaffbench-2) は、ある質問のうち最も難しい質問をしました — コーディング エージェントはできますか
スキャフォールダーを使用せずに、プロンプトから実際のフルスタック プロジェクトを手書きで作成し、ビルドできるでしょうか?答えは
「まれに」でした。

ScaffBench 2.1 は、最新モデル **Claude Sonnet 5** をテストします - **Claude との直接対決
Opus 4.8** は、**13 のハード仕様の拡張スイート上で、低推力と最大推論の両方で実行されます。
8 つのエコシステム**。また、**Sonnet 4.6**、**GPT-5.3 Codex Spark**、および Google の Antigravity 経由で実行しました。

生の機能の尺度: エージェントは仕様を読み取り、すべてのファイル自体を書き込みます。

3 つの構成すべてが 13 スペックの完全な実行を完了しました。状況は次のとおりです。

- **8 つのエコシステム、13 の仕様** TypeScript、Rust、Python、Go、.NET、そして現在は **Java** (Spring + jOOQ +
  Keycloak) と **Elixir** (ブロードウェイ + アブサン)、さらに Expo React Native アプリとマルチエコシステム
  グラフ — それぞれが選択されているため、自信のあるエージェントが「近い」近傍を選択し、それを微妙に間違えることができます。
- **フロンティア、プロンプトのみの仕様。** 2 つの仕様は、意図的に当社独自のジェネレータのオプション領域を超えています。
  したがって、それらはプロンプト パス上でのみ実行されます。どの足場もそれらを「騙す」ことはできません。
- **実際の原価計算。** Claude コードは、サブスクリプションに関する `$0` を報告します。これにより、有能なモデルのように見えます。
  無料。現在、各実行の価格はトークンの使用量に基づいて計算されています。これにより、上記の最大エフォートコストが均等になります。
  見える。
- **エンドツーエンドで検証済み。** グレーディング ホスト上の .NET SDK を使用すると、.NET およびマルチ .NET の仕様は次のようになります。

Sonnet の 3 つの仕様と Opus の 2 つはクリーン ビルドの判定ではなく、ベンチマークは役に立つだけです

<Callout kind="warn">

  サブディレクトリ (`frontend/package.json`、`backend/go.mod`) 内のマニフェストを使用してプロジェクトをビルドしましたが、

## テイクアウト

- **Sonnet 5 はスタックを認識していますが、アセンブルするビルドの数は少なくなります。** ライブラリの選択にフィールドを結び付けます。
  (約 96% が有線) ですが、実際にコンパイルしたプロジェクト (2/10 対 Opus の 3/11) を追跡しながら、ほとんどのことを実行しています。
  そこに到達するために作業します (プロジェクトあたり 215 ステップ)。これには独自の強みがあります。それが唯一の構成です。
  Elixir 仕様を構築しました。
- **推論の努力は手段ではありません。** Opus は最大でも低でも同じ 3/11 を 5 ～ 10 倍のコストで構築しました —
  追加の審議により、スタックの数ではなく、どのスタックが集まるかが再シャッフルされます。
- **スタックの選択は解決されました。一貫性のあるアセンブリではありません。** 9 ～ 27% のビルド レートで ~92 ～ 97% が配線されるのは、
  全体のストーリーを 1 行で説明します。現場のすべてのモデルに当てはまり、足場が埋める隙間も正確にわかります。
  これが、ScaffBench 2 の MCP パスと CLI パスが 100% 近くにとどまる一方、プロンプトのみが困難である理由です。

より多くのモデルが登場するにつれて、リーダーボードは成長し続けます。

Використовуйте цей стек, якщо вам потрібен Rust як на стороні сервера, так і на зовнішній стороні створеної програми.

```npm
npm create better-fullstack@latest my-rust-fullstack -- \
  --ecosystem rust \
  --rust-web-framework axum \
  --rust-frontend leptos \
  --rust-orm sea-orm \
  --rust-api none \
  --rust-cli none \
  --rust-logging tracing \
  --rust-error-handling anyhow-thiserror
```

## Що це створює

- Сервер Rust на основі Axum.
- Leptos як варіант інтерфейсу Rust.
- SeaORM для доступу до бази даних.
- Трасування та структурована обробка помилок за замовчуванням.

## Згенерована форма

Цей стек є Rust-першою повноцінною програмою. Axum володіє середовищем виконання сервера, Leptos володіє поверхнею інтерфейсу, а SeaORM надає бекенду типізований рівень збереження.

Створена програма корисна, якщо потрібно, щоб одна робоча область Rust містила:

- Запуск сервера, маршрутизація та спільний стан.
- Види Leptos та інтерактивний код інтерфейсу користувача.
- Сутності бази даних і доступ до даних на стороні сервера.
- Логування та обробка помилок налаштовані з самого початку.

## Репрезентативне дерево файлів

Очікуйте макет, який відокремлює проблеми сервера від проблем інтерфейсу користувача, зберігаючи їх в одному проекті:

```txt
my-rust-fullstack/
  Cargo.toml
  .env.example
  src/
    main.rs
    app.rs
    error.rs
    routes/
      mod.rs
      api.rs
    entities/
      mod.rs
      user.rs
    pages/
      mod.rs
      home.rs
      users.rs
    components/
      mod.rs
```

Використовуйте згенероване дерево як орієнтир: компоненти Leptos повинні залишатися зосередженими на візуалізації та взаємодії, тоді як робота з базою даних має залишатися на стороні сервера.

## Приклади сервера та інтерфейсу користувача

Маршрут Axum може надавати кінцеві точки JSON для дій на стороні сервера або клієнтів інтеграції:

```rust
use axum::{extract::State, Json};
use serde::Serialize;

use crate::{error::AppError, AppState};

#[derive(Debug, Serialize)]
pub struct HealthResponse {
    pub status: &'static str,
}

pub async fn health(State(_state): State<AppState>) -> Result<Json<HealthResponse>, AppError> {
    Ok(Json(HealthResponse { status: "ok" }))
}
```

Сторінка Leptos повинна викликати функції сервера або помічники API, а не відкривати підключення до бази даних з коду інтерфейсу користувача:

```rust
use leptos::prelude::*;

#[component]
pub fn HomePage() -> impl IntoView {
    view! {
        <main>
            <h1>"Dashboard"</h1>
            <p>"Rust server, Rust UI, and one generated project shape."</p>
        </main>
    }
}
```

Для інтерфейсу користувача з базою даних зберігайте операцію з базою даних за межею сервера:

```rust
use sea_orm::{DatabaseConnection, EntityTrait};

use crate::entities::user;

pub async fn list_users(db: &DatabaseConnection) -> Result<Vec<user::Model>, sea_orm::DbErr> {
    user::Entity::find().all(db).await
}
```

## Примітки щодо сумісності

У цьому посібнику використовуються прапорці, специфічні для Rust, замість прапорців інтерфейсу/бекенду TypeScript. Зберігайте вибір інтерфейсу Rust під `--rust-frontend`.

Прапорці `--rust-api none` та `--rust-cli none` зосереджують цей каркас на веб-програмі. Додайте опцію gRPC або CLI лише тоді, коли згенерований проект навмисно обслуговує кілька інтерфейсів. Якщо вам потрібен лише бекенд API, використовуйте `--rust-frontend none` та натомість дотримуйтеся посібника Axum API.

## Коли його вибрати

Виберіть це, якщо проект отримує переваги від архітектури Rust-first за межами додатків і вашій команді подобається модель часу компіляції Rust.

Він чудово підходить для внутрішніх інструментів, поверхонь адміністратора та областей продуктів, де спільне використання типів Rust і перевірка на сервері та інтерфейсі користувача є більш цінним, ніж впровадження зовнішньої екосистеми JavaScript.

## Компроміси

Fullstack Rust зменшує перемикання мов, але робочий процес інтерфейсу відрізняється від React, Vue або Svelte. Заплануйте час компіляції Rust, шаблони маршрутизації для Leptos і команду, якій буде зручно налагоджувати поведінку браузера за допомогою згенерованого Rust коду інтерфейсу користувача.

## Примітки щодо тестування та розгортання

Використовуйте модульні тести Rust для служб і логіки моделі, а потім додайте тести на рівні маршруту або браузера навколо найважливіших потоків.

```bash
cargo test
```

Для розгортання перевірте обидві половини програми: сервер має отримати змінні середовища, а зовнішні ресурси мають бути створені за допомогою згенерованих сценаріїв проекту. Зберігайте міграції бази даних у шляху розгортання, якщо програма зберігає дані користувача.

## Усунення несправностей

- Якщо інтерфейс користувача створюється, але дані сервера відсутні, перевірте, чи маршрут сервера або функція сервера зареєстровано в маршрутизаторі Axum.
- Якщо типи баз даних змінюються, повторно створіть або оновіть сутності SeaORM за допомогою робочого циклу документів каркасу.
- Якщо маршрут браузера працює локально, але не після розгортання, перевірте разом згенеровану маршрутизацію сервера та конфігурацію статичних активів.
- Якщо журнали надто тихі, встановіть `RUST_LOG=info` перед запуском сервера.

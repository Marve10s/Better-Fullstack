Використовуйте цей стек, коли вашій програмі TanStack Start потрібна трансакційна електронна пошта для проходження входу, сповіщень про продукт, запрошень або повідомлень про адаптацію.

```npm
npm create better-fullstack@latest my-email-app -- \
  --ecosystem typescript \
  --frontend tanstack-start \
  --backend self \
  --database sqlite \
  --orm drizzle \
  --auth better-auth \
  --email resend \
  --api trpc \
  --css-framework tailwind \
  --ui-library shadcn-ui \
```

## Що це створює

- Програма TanStack Start з власним рівнем маршрутизації сервера.
- Повторно надіслати як варіант постачальника послуг електронної пошти.
- Better Auth з підтримкою реляційної бази даних.
- Drizzle та SQLite для місцевого розвитку.
- Tailwind CSS і shadcn/ui для інтерфейсу.

## Згенерована форма

Цей стек починається з форми повного стека TanStack Start і додає конфігурацію постачальника електронної пошти. Постачальник електронної пошти вибрано за допомогою `--email resend`; решта програми все ще використовує `--backend self`, тому вам не потрібен окремий сервер API лише для надсилання пошти.

Представницька форма:

```txt
my-email-app/
  bts.jsonc
  src/
    routes/
    lib/
      auth/
      db/
      email/
```

Розглядайте наведене вище дерево як керівництво щодо володіння, а не як обіцянку точних згенерованих шляхів. Код доставки електронної пошти має зберігатися за невеликим помічником лише для сервера, щоб компоненти React ніколи не імпортували секрети постачальника.

## Приклад електронного помічника

Гарною першою абстракцією є вузька функція для кожного електронного листа продукту. Завдяки цьому деталі повторного надсилання не потрапляють у зворотні виклики автентифікації, потоки адаптації та обробники маршрутів:

```ts
type SendInviteEmailInput = {
  to: string;
  inviterName: string;
  inviteUrl: string;
};

export async function sendInviteEmail(input: SendInviteEmailInput) {
  const subject = `${input.inviterName} invited you`;

  return sendTransactionalEmail({
    to: input.to,
    subject,
    html: `
      <p>${input.inviterName} invited you to join their workspace.</p>
      <p><a href="${input.inviteUrl}">Accept the invite</a></p>
    `,
  });
}
```

Конкретна реалізація `sendTransactionalEmail` повинна зчитувати ключ Resend API зі змінних середовища сервера та не повинна імпортуватися з клієнтських компонентів.

## Приклад використання маршруту

Надсилайте пошту після транзакції бази даних, яка створює довговічний стан продукту. Для запрошень спочатку створіть запис запрошення, а потім надішліть електронний лист:

```ts
import { z } from "zod";

const inviteInput = z.object({
  email: z.string().email(),
  workspaceId: z.string().min(1),
});

export async function inviteMember(rawInput: unknown) {
  const input = inviteInput.parse(rawInput);

  const invite = {
    id: crypto.randomUUID(),
    email: input.email,
    workspaceId: input.workspaceId,
  };

  await sendInviteEmail({
    to: invite.email,
    inviterName: "A teammate",
    inviteUrl: `https://example.com/invites/${invite.id}`,
  });

  return invite;
}
```

Для виробничих систем розгляньте чергу завдань або таблицю повторів для електронних листів, які мають бути доставлені, навіть якщо постачальник має тимчасовий збій.

## Коли його вибрати

Виберіть це, якщо електронна пошта є частиною робочого процесу продукту, а не задумом. Повторне надсилання добре підходить для транзакційної електронної пошти, орієнтованої на розробників, і зберігає згенерований стек простим.

## Загальні випадки використання

- Чарівні посилання та електронні листи для підтвердження.
- Команда запрошує.
- Пробні або вступні електронні листи.
- Сповіщення про продукт від дій сервера або маршрутів API.

## Примітки щодо сумісності

- `--email resend` є адитивним. Він не замінює `--auth better-auth`, `--api trpc` або `--backend self`.
- Доставка електронної пошти має виконуватися на стороні сервера. Ніколи не відкривайте ключ Resend API через загальнодоступні змінні середовища або пакети браузера.
- SQLite зручний для локальної розробки. Якщо робочі процеси електронної пошти залежать від надійних журналів аудиту, повторних спроб або записів командного масштабу, PostgreSQL може бути кращою робочою базою даних.
- Потоки електронної пошти Better Auth та потоки сповіщень про продукт повинні мати спільну конфігурацію постачальника, але залишатися розділеними на функціональному рівні.

## Примітки до розгортання

Налаштуйте ключ Resend API, домен відправника, секрети Better Auth та URL-адресу програми в середовищі розгортання. Перевірку домену слід завершити, перш ніж покладатися на доставку робочої пошти.

Для попереднього розгортання використовуйте обмежений відправник або список дозволених одержувачів, якщо ваша програма може ініціювати електронні листи від ненадійного трафіку попереднього перегляду.

## Усунення несправностей

- Якщо електронні листи не надходять, перевірте журнали постачальника, перш ніж змінювати код програми.
- Якщо посилання вказують на localhost, оновіть URL-адресу робочої програми, яка використовується під час створення посилань зворотного виклику або запрошення.
- Якщо електронні листи автентифікації працюють, але електронні листи продуктів не працюють, переконайтеся, що обидва шляхи використовують ту саму конфігурацію постачальника лише для сервера.
- Якщо локальні тести випадково надсилають справжню електронну пошту, додайте транспорт розробки або охорону навколо невиробничих середовищ.
